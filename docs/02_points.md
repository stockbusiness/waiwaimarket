# 02 オーリーポイント仕様（最重要）

出典：v1.4 4.4、6章

## 4 4 ポイント負担

| **付与区分** | **負担者** |
| --- | --- |
| 基本還元 | マーケット運営本部 |
| テナント独自の上乗せ | 対象テナント |
| 店舗・カテゴリー限定企画 | マーケット運営本部または対象テナント |
| 全体キャンペーン | マーケット運営本部 |

本部負担ポイントが利用された場合、テナントの受取額は値引き前の商品代金を基準に計算し、ポイント利用分は本部負担として精算時に補填する。テナント負担ポイントの場合は精算額から控除する。

本部負担ポイントは、将来の値引きに使用される可能性があるため、未使用残高を額面ベースの最大値引き原資として管理する。会計上の区分は現金債務と断定せず、顧客との契約内容を基に税理士または会計士へ確認する。

購入時の基本還元1％は、購入者に表示した条件どおり付与し、予算到達を理由に停止しない。売上に連動する基本還元見込額を月次で予測し、警告基準額を設定する。

本部負担の上乗せキャンペーンには月次発行予算とハード上限を設定する。上限到達時は新規の上乗せ付与を停止し、基本還元のみ継続する。管理画面では未使用残高、基本還元額、キャンペーン発行額、利用額、失効額を分けて確認できるようにする。


# 6 オーリーポイント仕様

## 6 1 初期ルール

| **項目** | **初期値** |
| --- | --- |
| 基本還元率 | 税込商品代金の1％ |
| 送料 | 付与対象外 |
| ポイント利用分 | 付与対象外 |
| 付与単位 | 注文明細（order_item）単位。注文全体の付与数との差は最大剰余方式で配分する |
| 獲得状態 | 付与予定 → 利用可能 |
| 確定時期 | 発送登録日＋14日。配送完了検知はMVPで実装しない |
| 有効期限 | ロット単位の固定期限。付与日から12か月。獲得ごとの期限延長は初期では採らない |
| 消費順序 | 有効期限の近いロットから消費（FIFO） |
| 利用価値 | 1ポイント＝1円相当の値引き |
| 利用上限 | 注文ごとに商品代金（税込・送料除く）の50％まで。全額ポイント購入は不可 |
| 基本還元の月次警告基準額 | 管理設定。初期値はフェーズ0で決定。到達しても購入時の基本還元は継続する |
| 上乗せキャンペーンの月次上限 | 管理設定。初期値はフェーズ0で決定。到達後は上乗せ付与を停止する |
| 現金化・送付 | 不可 |

還元率、有効期限、確定日数、利用上限、警告基準額、キャンペーン上限はハードコードせず、管理画面から変更可能にする。変更は既存注文へ遡及適用せず、注文確定時のルールを保存する。

購入時の獲得ポイント総数は、注文内の付与対象額合計に還元率を掛け、小数点以下を切り捨てて求める。各明細には明細金額に還元率を掛けた整数部分を先に割り当て、注文全体との差を小数部分が大きい明細から1ポイントずつ配分する。同率の場合はorder_item_id順とし、再計算しても同じ結果になるようにする。

利用上限を50％とする理由は、円決済ゼロの注文を発生させず、決済アダプターに特殊経路を持たせないためである。

## 6 2 ポイント台帳と状態

point_ledger_entriesは、残高増減を表す変更不可のイベント台帳とする。記録済みの行を更新・削除せず、取消や訂正は反対取引を追加する。

台帳のentry_typeは次のとおりとする。

1. earn_pending：付与予定。

2. earn_confirmed：利用可能残高への確定。

3. spend：注文へのポイント利用。

4. spend_refund：返品・取消による利用ポイントの返還。

5. earn_reversal：付与予定または確定済みポイントの取消。

6. expire：有効期限切れ。

7. adjustment：承認済みの手動調整。

point_lotsはpending、available、exhausted、expired、reversedの状態を持つ。point_reservationsはactive、committed、released、expiredの状態を持つ。購入手続き中の予約ポイントは利用可能残高から除外する。

残高だけを直接増減させない。すべての変動を台帳へ記録し、台帳の合計から残高を算出できる構造にする。

## 6 3 注文時の処理

1. 購入者が利用ポイント数を入力する。

2. サーバー側で利用可能残高（予約中を除く）と注文上限（50％）を再確認する。

3. 対象ロットを期限の近い順に予約し、point_reservationsへ記録する。有効期限は在庫引当と同じ15分とする。

4. 予約したロット、使用数、注文、注文明細の対応をpoint_usage_allocationsへ保存する。利用ポイントは対象明細の付与対象額に応じて最大剰余方式で配分する。

5. 円決済に成功したら予約をcommittedにし、spendを台帳へ記録する。

6. 円決済に失敗・中断・期限切れとなったら予約を解除する。

7. 6.1の計算方法で注文明細ごとの獲得予定ポイントを算出し、earn_pendingを台帳へ記録する。注文時点の還元率、期限、負担者、計算結果を保存する。

8. 発送登録日＋14日を経過したらearn_confirmedを記録し、対象ロットをavailableにする。バッチ処理は冪等とする。

## 6 4 返品と返金時の処理

購入で付与予定だったポイントは、返金対象明細に対応するearn_reversalを記録する。

すでに利用可能になった付与ポイントも、返金対象明細に対応するearn_reversalを記録し、対象ロットの残量を減らす。

注文に使用したポイントは、point_usage_allocationsに保存した明細別・ロット別の使用数を基に返還する。割合計算だけで推定しない。数量の一部を返品する場合は、対象数量の比率を基に整数計算し、端数は同じ最大剰余方式で決定する。

返還ポイントはspend_refundとして記録し、元ロットの有効期限を引き継ぐ。元の有効期限を過ぎている場合は即時失効とする。購入者保護の観点から最低利用期間を設ける場合は、ポイント規約で別途決定する。

反対取引により残高がマイナスになる場合は、残高をマイナスのまま記録し、次回付与で相殺する。残高が0未満の間はポイント利用を停止し、購入者への現金請求は行わない。この扱いをオーリーポイント規約へ明記する。

## 6 5 二重処理防止

• 決済通知、発送登録、返金処理は同じ通知が複数回届く前提で設計する。

• すべての付与・利用・取消に一意な処理キーを持たせる。

• order_item_id + event_type + sequence 等で重複を拒否する。

• 同時購入時はポイント口座行または対象ロットをロックする。

• 決済成功とポイント利用の整合性、および台帳合計と口座残高の一致を日次で照合する。
