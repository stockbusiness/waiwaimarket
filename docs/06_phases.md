# 06 実装フェーズと対象外機能

出典：v1.4 10章、11章、4.1、4.2

## 4 1 一般公開と会員登録

商品一覧、商品詳細、店舗ページはログイン不要で閲覧可能とする。

購入時にはメール認証を行い、このマーケット専用の購入者アカウントを作成する。完全なゲスト購入は初期MVPでは採用しない。本人確認不能、ポイント統合、問い合わせ対応の複雑化を避けるためである。

LINEは「ログイン連携」として既存のメールアカウントに紐づける方式とし、LINE単独のアカウントは作成しない。1購入者＝1メールアドレス＝1ポイント口座を維持し、アカウント統合の問題を発生させない。

ポイントはマーケット専用の購入者IDに対して付与する。千ノ国共通IDへの依存は持たせない。

## 4 2 カートと注文

初期MVPは「1回の決済につき1テナント」の注文とする。

複数テナントの商品を一度に決済すると、送料、発送、部分キャンセル、返金、ポイント、テナント精算が急激に複雑になる。画面上では商品を店舗別にまとめ、別々に購入手続きを行えるようにする。

複数テナント横断の一括決済は、第2段階で必要性と決済手段を確認してから追加する。

在庫引当は購入手続き開始（checkout/preview）時に行い、有効期限を15分とする。期限切れの引当は自動解放する。カート投入時には引当しない。


# 10 実装フェーズ

## フェーズ0 独立サービス設計決定 1から2週間目安

1. マーケットの正式名称、対象商品、初期テナントを決定する。

2. Stripe Connectの利用申請を行い、契約条件を確認する（審査待ちが全体のクリティカルパスになるため最初に着手）。

3. 販売者、Stripe上の事業主体、on_behalf_of、領収書・適格請求書、収納代行・資金移動業、会計処理について専門家確認を行い、規約・契約書の文言を確定する。

4. 基本還元の月次警告基準額と、上乗せキャンペーンの月次発行上限を決定する。

5. 商品カテゴリー、禁止商品、返品・送料の基本ルールを確定する。

6. 画面一覧、権限表、DB設計、API設計を作成する。

**完了条件：Stripe Connect申請済み、専門家確認済み、DB設計・権限表が承認されている。**

## フェーズ1 共通基盤とテナント管理 2から3週間目安

1. マーケット専用の会員登録・メール認証ログインを実装する。

2. 購入者、テナント管理者、テナント担当者、本部管理者、本部オペレーターの権限、RLS、API認可、Storage Policyを実装する。

3. 出店申請、審査、停止を実装する。

4. Stripe Connectオンボーディングを審査フローに組み込む。

5. 店舗ページと特商法情報を実装する。

6. 監査ログを実装する。

7. 本部管理者の多要素認証とサービスロールキーの利用制限を実装する。

**完了条件：申請からStripeオンボーディング完了・本部承認まで通しで動作し、未承認テナントは出品できない。**

## フェーズ2 商品と在庫と公開画面 2から3週間目安

1. 商品・SKU・画像・カテゴリー管理を実装する。

2. 商品審査と差戻しを実装する。

3. 在庫引当（TTL15分）、自動解放、在庫切れ制御を実装する。

4. 一般公開の商品一覧、商品詳細、店舗ページを実装する。

5. スマートフォン表示とアクセシビリティを確認する。

**完了条件：承認商品だけが公開され、同時購入でも在庫超過販売が発生しない。**

## フェーズ3 カートと注文と決済と配送 4から5週間目安

1. 1テナント単位のカートを実装する。

2. 送料・税・合計金額のサーバー側再計算を実装する。

3. Stripe Connect（Destination charges、on_behalf_of）を決済アダプター経由で接続する。

4. 注文状態遷移を実装する。

5. 発送・追跡番号・購入者通知を実装する。

6. キャンセル、全額返金、部分返金、reverse_transfer、販売手数料返還を実装する。

7. チャージバック管理、テナントからの回収、残高不足時の出金保留を実装する。

8. テナント名義の領収書・適格請求書発行を実装する。

**完了条件：テスト決済で注文、発送、取消、全額返金、部分返金、領収書発行まで再現できる。**

## フェーズ4 オーリーポイント 2から3週間目安

1. ポイント台帳・付与ロット・期限管理を実装する。

2. 注文時のポイント予約（TTL15分）、ロット割当、明細割当、利用を実装する。

3. 明細単位の予定付与と、発送登録日＋14日の確定バッチを実装する。

4. 返品時の返還・取消・マイナス残高処理を実装する。

5. 基本還元の警告基準額、キャンペーン発行上限、未使用残高、最大値引き原資の集計を実装する。

6. マーケット会員マイページへ残高・履歴を表示する。

7. 管理者のルール設定・手動調整・監査を実装する。

**完了条件：同一決済通知を複数回送っても二重付与されず、返品後の円・ポイント・精算額が一致する。**

## フェーズ5 テナント精算と本部運用 2から3週間目安

1. 商品代、送料、手数料、ポイント負担、返金を明細化する。

2. テナント別の精算予定・確定・支払済み状態と、Stripe手動出金の実行を実装する。

3. 精算CSV・会計連携用データを出力する。

4. 問い合わせ、違反商品、テナント停止時の運用を整備する。

5. 本番監視、バックアップ、障害対応手順を整備する。

**完了条件：テスト月次精算について、注文合計と決済・返金・ポイント・手数料・振込額が一致する。**

## フェーズ6 限定テナントで試験運用 2から4週間目安

• テナント3～5社

• 商品20～50点

• 社内・関係者による購入テスト

• その後、限定した一般購入者へ公開

確認項目は購入完了率、問い合わせ件数、発送遅延、在庫差異、返金率、チャージバック率、ポイント利用率、精算差異、本部負担ポイントの未使用残高と最大値引き原資とする。

判断基準：購入完了率が低い、または問い合わせが多い場合は、購入導線のUI改善を最優先し、ポイント機能の拡張は停止する。この基準を試験運用開始前に数値で確定する。

全フェーズの目安は15～23週間である。Stripe審査、専門家確認、テナント本人確認の待機期間は別途バッファとして管理する。

# 11 MVPで実装しない機能

• 複数テナント商品の一括決済

• 越境EC、多通貨、多言語決済

• 定期購入

• オークション、フリマ、ユーザー間取引

• ライブコマース

• 高度なレビュー・ランク制度

• ポイントの購入、換金、送付、外部交換

• ポイント有効期限の獲得ごとの延長

• 配送完了の自動検知（追跡API連携）

• トークン、ブロックチェーン化

• NFTマーケット、ウォレット、パスポート、代理店システムとの連携

• Unity等のメタバース連携

これらを先に入れると、販売開始が遅れ、運用検証前の開発費が膨らむためである。
