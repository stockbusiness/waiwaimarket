# 00 概要と基本方針

出典：一般物販マーケット オーリーポイント実装計画 v1.4（1〜3章、5章、8章）

# 1 目的

一般の購入者が商品を購入でき、審査を通過したテナントが自ら商品を出品・受注・発送できる一般物販マーケットを、独立したECサービスとして構築する。

購入者にはオーリーポイントを付与し、マーケット内の値引き・特典に利用できるようにする。初期段階ではマーケット内だけで付与・利用・管理を完結させる。

NFTマーケット、NFT、千ノ国メタバース、千ノ国ウォレット、千ノ国パスポート、代理店システムとは接続しない。当面は別システムとして運営し、統合はメタバース側の事業成立後に別プロジェクトとして連携可否を判断する。

オーリーポイントは暗号資産・トークンではない。将来もトークンへの変換を予定せず、換金・売買・ユーザー間送付はできないマーケット内専用ポイントとする。

# 2 成功条件

システムの完成ではなく、次の状態を初期成功とする。

1. 一般購入者がスマートフォンから迷わず商品を購入できる。

2. テナントが本部の支援なしでも商品登録、在庫更新、受注確認、発送通知を行える。

3. 本部が出店者・商品・注文・返金・精算・ポイントを一元管理できる。

4. 返品や決済再送が発生しても、ポイントが二重付与されない。

5. 購入者が獲得理由、有効期限、利用履歴を確認できる。

6. NFT・メタバース関連システムが停止・変更されても、マーケットが単独で運営できる。

7. 本部が負担するポイントについて、未使用残高、最大値引き原資、月次発行額、利用額、失効額を常時把握できる。

# 3 確定する基本方針

| **項目** | **方針** |
| --- | --- |
| マーケット名 | 正式名称は別途決定。実装上は独立した一般物販マーケットとして扱う |
| 対象 | 一般購入者が利用できる物販マーケット |
| 出店方式 | 本部審査を通過したテナントのみ出店可能 |
| 法律上の販売者 | 各テナント（テナント型マーケットプレイス） |
| Stripe上の事業主体 | on_behalf_ofを用いて対象テナントを決済上の事業主体として指定する。Stripe審査結果と専門家確認で最終確定する |
| 集金 | 本部のStripeアカウントで決済を作成し、販売手数料を除く金額をテナントのStripe残高へ移動する |
| 銀行口座への出金 | テナントのStripe残高から手動出金する。初期サイクルは月末締め・翌月15日払い |
| 配送 | 各テナントが担当する |
| 本部の役割 | 場の提供、審査、決済管理、精算、問い合わせ一次受付、ポイント運営 |
| ポイント名称 | オーリーポイント |
| ポイントの性質 | 無償付与されるマーケット内専用ポイント |
| トークン化 | 行わない |
| 換金・譲渡 | 不可 |
| 初期用途 | マーケットの商品購入値引き・マーケット内特典 |
| メタバース連携 | MVP対象外。利用者向けにも訴求しない |
| NFTマーケット連携 | 行わない。DB・注文・決済・管理画面を分離する |
| 技術方針 | 一般的なマルチテナントECとして単独稼働させる。構成は8.2参照 |


# 5 利用者別のMVP機能

## 5 1 一般購入者

• 商品一覧・商品詳細の閲覧

• カテゴリー、キーワード、店舗による検索

• 店舗ページの閲覧

• カート追加

• 配送先登録

• 決済

• 注文履歴・配送状況確認

• キャンセル・返品申請

• ポイント残高、獲得予定、利用履歴、有効期限の確認

• 購入時のポイント利用

• メールまたはLINEによる注文・発送通知

• 領収書の表示・ダウンロード

## 5 2 テナント

• 出店申請

• 事業者情報、特定商取引法表記、適格請求書登録番号、振込先（Stripeオンボーディング）、返品条件の登録

• 店舗情報、ロゴ、紹介文、ストーリーの編集

• 商品登録、編集、公開申請、販売停止

• 商品画像、価格、税区分、在庫、送料、発送日数の登録

• 受注確認

• 発送処理、追跡番号登録

• キャンセル・返品対応

• 売上、手数料、ポイント負担、精算予定額の確認

• CSV出力

## 5 3 本部管理者

• テナント審査、承認、停止

• 商品審査、承認、差戻し、販売停止

• カテゴリー・特集管理

• 全注文、決済、返金、配送状況の確認

• テナント別手数料率設定

• 送料ルール確認

• ポイント基本還元率・利用上限・有効期限・確定日数・基本還元の警告基準額・キャンペーン発行上限の設定

• 商品別・店舗別・キャンペーン別のポイント設定

• ポイント手動付与・取消（理由、実行者、承認履歴必須）

• 未使用ポイント残高・最大値引き原資・基本還元額・キャンペーン発行額・利用額・失効額の確認

• テナント別精算額の確定・出力・送金実行

• 操作ログ、監査ログ確認

• 禁止商品・違反商品の管理

## 5 4 役割と権限

| **役割** | **範囲** |
| --- | --- |
| 購入者 | 自分の注文・ポイント・配送先のみ |
| テナント管理者 | 自店舗の全機能、担当者の追加・削除、精算情報 |
| テナント担当者 | 自店舗の商品・受注・発送（精算・事業者情報は閲覧不可） |
| 本部管理者 | 全機能、ルール設定、精算確定、手動調整の承認 |
| 本部オペレーター | 審査・問い合わせ・注文確認（ルール変更・精算確定・手動調整は不可） |

購入者・テナント・本部は別ログイン画面・別セッションとする。


# 8 システム構成

• 購入者・テナント・本部 → 一般物販マーケット

• 一般物販マーケット → マーケット会員

• 一般物販マーケット → 商品・注文・決済・配送

• 一般物販マーケット → オーリーポイント台帳

• 商品・注文・決済・配送 → テナント精算 → Stripe残高と銀行口座への出金

## 境界の原則

• マーケット会員：購入者の認証、連絡先、配送先を管理する。

• マーケット：店舗、商品、在庫、注文、配送、返金、精算を管理する。

• ポイント基盤：オーリーポイントの付与・利用・取消・期限をマーケット内部で管理する。

• 会員マイページ：ポイント残高と履歴を表示する。別のウォレットアプリは使用しない。

• NFT・メタバース・代理店関連システムとはAPI、DB、認証を共有しない。

## 8 1 独立運用の分離ルール

• 新しいリポジトリとして構築する。

• 専用データベース（専用Supabaseプロジェクト）を使用し、NFTマーケットのテーブルを流用しない。

• 専用ドメインまたは専用サブドメインで公開する。

• 購入者・テナント・本部の認証をマーケット内で完結させる。

• 管理画面、決済、注文番号、問い合わせ窓口、利用規約を分ける。

• ユーザー向け画面や販促文では、NFTやメタバースを購入理由として訴求しない。

• 将来連携を見越した専用APIはMVPでは作らず、各IDをUUIDで管理して移行可能性だけを残す。

## 8 2 技術構成

| **層** | **採用** |
| --- | --- |
| フロント／API | Next.js（App Router） |
| DB・認証 | Supabase（専用プロジェクト）。RLS、API認可、Storage Policy、サービスロール分離を組み合わせる |
| 決済 | Stripe Connect（Expressアカウント、Destination charges、on_behalf_of、manual payouts、debit_negative_balances） |
| ホスティング | Vercel（Tokyoリージョン） |
| メール | Resend |
| LINE | LINEログイン（連携のみ）、Messaging API（通知） |
| バッチ | ポイント確定・失効・引当解放・日次照合をVercel Cron等で実行。すべて冪等とする |

グループの既存プロダクトと同一スタックにし、Claude Code向けの開発指示テンプレート、運用手順、監視設定を流用する。

RLSだけで情報保護を保証しない。すべてのAPIでサーバー側認可を行い、商品画像と本人確認関連ファイルにはStorage Policyを設定する。サービスロールキーはサーバー専用とし、通常処理では使用範囲を限定する。本部管理者には多要素認証を必須とする。
